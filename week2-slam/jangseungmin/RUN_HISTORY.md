# 실행 이력과 실패 분석

이 문서는 TurtleBot3 Nav2 과제를 준비하면서 수행한 실행을 성공 여부와 관계없이 기록한다. 최종 제출 영상과 성공 결과는 `media/`에 두고, 실패한 실행의 JSON과 영상은 `evidence/attempts/`에 보존한다.

## 실행 이력

| 시도 | 목표 또는 작업 | 결과 | 확인된 원인 | 다음 조치 |
|---|---|---|---|---|
| A01 | 시뮬레이션 준비 전 목표 전송 | `TIMED_OUT` | 지도, 센서, TF, Nav2가 준비되지 않은 상태에서 목표 전송 | 시뮬레이션을 먼저 실행하고 `Navigation`, `Localization`의 Active 상태 확인 |
| A02 | 기본 목표 `(1.5, -0.5, 0.0)` | `SUCCEEDED` | 기본 구성의 자율주행 동작 확인 | 개인 목표로 변경해 재현 시도 |
| A03 | 기본 목표 주행과 자동 화면 수집 병행 | `ABORTED` | 화면 수집 부하가 커진 상태에서 제어 및 액션 처리가 지연됨 | 3D LiDAR를 끄고 Gazebo GUI를 숨긴 촬영 설정 사용 |
| A04 | 개인 목표 `(1.8, 0.6, 1.57)`, `navigation-run.json` | `ABORTED` | 녹화 부하 중 주행이 조기 종료됨. 해당 실행의 BT 종료 로그는 보존되지 않아 세부 원인은 미확정 | 도착 방향을 `0.0 rad`로 단순화하고 재실행 |
| A05 | 개인 목표 `(1.8, 0.6, 0.0)`, `navigation-run_0.json` | `ABORTED` | `compute_path_to_pose` 목표 승인 응답이 `default_server_timeout=20 ms`를 초과 | 개인 override에서 제한 시간을 `2000 ms`로 확대 |
| A06 | 개인 목표 `(1.8, 0.6, 0.0)`, `navigation-run_1.json` | `ABORTED` | A05와 동일한 경로 계산 액션 승인 시간 초과 | 변경된 파라미터가 실행 노드에 적용됐는지 직접 확인 |
| A07 | 개인 목표 `(1.8, 0.6, 0.0)`, `navigation-run-3.json` | `TIMED_OUT` | 서버 승인 문제는 해결됐으나 180초 동안 남은 거리가 `4.92 m`에서 `2.05 m`까지만 감소 | 주행 제한 시간 확대와 RViz 표시 최소화 후 재실행 |
| A08 | 개인 목표 `(1.8, 0.6, 0.0)`, `navigation-run-4.json` | `SUCCEEDED` | `default_server_timeout=2000 ms`, 주행 제한 `420 s` 적용. 198.475초 후 위치 오차 `0.140 m`로 도착 | 성공 JSON·RViz 캡처·편집 영상을 최종 제출물로 선정 |

## 설정 변경의 근거

`default_server_timeout`은 Behavior Tree가 planner와 controller의 액션 서버 응답을 기다리는 시간이다. 기존 `20 ms` 설정에서는 WSL, RViz, 화면 녹화를 함께 실행할 때 `compute_path_to_pose` 요청이 즉시 중단됐다. 이를 `2000 ms`로 늘린 뒤에는 목표가 승인되고 실제 주행이 시작됐다. A06에서 남은 거리가 계속 감소한 점으로 이 변경의 효과를 확인했다.

A07의 실패 원인은 경로 계산이 아니라 `navigate_to_goal.py`의 전체 주행 제한 시간이었다. 같은 목표에 `--timeout 420`을 적용한 A08은 198.475초 후 `SUCCEEDED`로 종료됐다.

A03 이후에는 제출 화면에서 3D LiDAR를 기본적으로 끄고 RViz 표시 속도를 20 fps로 낮췄다. 최종 촬영에서는 Gazebo GUI도 숨겨 지도, 로봇, 전역 경로와 Nav2 상태를 확인하는 데 필요한 화면에 자원을 집중했다. 이는 센서나 물리 시뮬레이션을 끈 것이 아니라 시각화 부하만 줄인 조치다.

최대 선속도는 `0.22 m/s`에서 `0.18 m/s`로 낮춰 경로 추종을 관찰하기 쉽게 했다. 이 설정은 주행 시간을 늘리는 대신 촬영 중 로봇의 움직임을 확인하기 쉽다는 절충이다. 위치와 방향의 도착 허용 오차는 각각 `0.25`에서 `0.15`로 줄였다. 이 값은 실패 자체를 해결하는 시간 설정이 아니라, 여러 번의 중단을 겪은 뒤 목표 근처에 보이는 것만으로 성공 처리하지 않기 위해 유지한 검증 기준이다. 최종 실행은 위치 오차 `0.140 m`, yaw 오차 `0.150 rad`에서 Nav2의 `SUCCEEDED` 판정을 받았다.

## 운영 중 확인한 문제

- Windows에서 받은 셸 스크립트의 CRLF 줄바꿈 때문에 `set: pipefail` 오류가 발생했다. 셸 파일을 LF로 정규화하고 `.gitattributes`에 `*.sh text eol=lf`를 추가했다.
- OBS의 창 캡처가 WSLg RViz 창을 검은 화면으로 표시했다. 디스플레이 캡처로 전환했다.
- 같은 출력 경로를 다시 사용하면 기존 JSON을 보호하기 위해 실행이 중단된다. 시도별 고유 파일명을 사용한다.

## 최종 판정 기준

최종 실행은 터미널의 `SUCCEEDED`, RViz의 `Feedback: reached`, 성공 JSON의 최종 상태가 모두 일치할 때만 성공으로 판정한다. 로봇이 움직였거나 목표 근처에 도착한 화면만으로 성공 처리하지 않는다.
